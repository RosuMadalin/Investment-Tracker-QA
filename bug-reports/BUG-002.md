# BUG-002 — RapidAPI key is exposed in client-side code and in every browser request

**Related test case:** TC-16 (`../test-cases/test-cases.md`)
**Status:** Fixed (2026-09-22) — see Retest below
**Jira:** ITQ-3 — Investment Tracking-QA project

## Summary
The app calls the RapidAPI (Yahoo Finance) endpoints directly from the browser and sends its API key in the `x-rapidapi-key` request header. The key is also hardcoded in the published JavaScript files. Anyone who opens the browser DevTools (Network tab) or "View source" can read the key and use it with their own requests, consuming the app owner's RapidAPI quota.

## Environment
- Browser: Firefox 156
- OS: Windows 11
- Environment: Production — https://rosumadalin.github.io/Investment-Tracker/

## Preconditions
- App is loaded in the browser
- Browser DevTools are open on the **Network** tab, with the filter set to `rapidapi`

## Steps to Reproduce
1. Open the app and open DevTools (F12) → **Network** tab, filter by `rapidapi`
2. Enter a non-existent stock symbol (e.g. `GGGGGG`) in the "Enter Stock Symbol" field and click **+** (this triggers the symbol-validation call and does not write anything to the watchlist)
3. In the Network list, select the `GET get-price?region=US&symbol=GGGGGG` request to `yahoo-finance166.p.rapidapi.com`
4. In the **Headers** panel, scroll to **Request Headers**

## Actual Result
The request headers contain `x-rapidapi-host: yahoo-finance166.p.rapidapi.com` and `x-rapidapi-key: e960172fe6…` (full value visible in the browser; masked in the evidence screenshot). The request is initiated directly by `watchlist.js` from the visitor's browser (`Sec-Fetch-Site: cross-site`), so the key is sent to and readable by every visitor.

## Expected Result
No secret credential is present in client-side code or in requests visible to the visitor. Third-party API calls that need a secret key should go through a server-side component that holds the key.

## Root Cause (from source review)
The key is a string literal in the shipped JavaScript, used to build the request headers, in four places: `watchlist.js` (symbol validation and live price fetch), `charts.js` (historical data fetch) and `index.js` (news fetch). The app is a static site on GitHub Pages with no backend, so there is nowhere to keep a secret.

## Impact
- Anyone can reuse the key against RapidAPI. The response headers observed during the test show a free-plan hard limit of 500,000 requests (499,958 remaining at the time of the test), so abuse would exhaust the quota and break the app's prices, charts and news.
- The key (and the older commented-out ones) remain readable in the public repository's git history even after the source is fixed.

## Severity
Major — a credential is exposed to every visitor. Impact is bounded to the app's own RapidAPI quota (free plan, no user data involved), so it is not rated Critical.

## Priority
High

## Suggested Fix
Move the RapidAPI calls behind a small server-side proxy (e.g. a serverless function) that stores the key as a secret; the browser then calls the proxy instead of RapidAPI.

## Fix Applied (2026-09-22)
A Cloudflare Worker (`investment-tracker-proxy`) was deployed as a proxy: it forwards the same path and query string to RapidAPI, attaches `x-rapidapi-key` server-side from a Worker secret (never present in any repo), and only returns `Access-Control-Allow-Origin` for the app's own origin (`https://rosumadalin.github.io`). `watchlist.js`, `charts.js` and `index.js` were updated to call the Worker instead of RapidAPI directly, with no key or RapidAPI header left in the client-side code (commit `3f86d13`, Investment-Tracker repo).

Residual risk, accepted for this project: the key was not rotated, so the original value (and the two other, unused older keys found in code comments during the fix) remain readable in the app repo's git history. The Worker endpoint itself has no additional authentication, so it could still be called directly to consume the RapidAPI quota — a normal characteristic of a client-facing proxy without extra auth — but the RapidAPI credential itself is no longer exposed or reusable elsewhere.

## Retest (2026-09-22)
TC-16 re-executed against the live app (Firefox 156): the request now goes to `investment-tracker-proxy.madalinrosu.workers.dev` instead of `yahoo-finance166.p.rapidapi.com`, and its Request Headers no longer contain `x-rapidapi-key` or `x-rapidapi-host` — **PASS**. See `../screenshots/TC-16-retest-no-key.png`.

## Notes
- Out of scope for this bug: the Firebase configuration in `index.html` is a public client identifier by design; its protection depends on the Firestore security rules, and unauthenticated Firestore access was already documented as an observation in `../test-summary/test-summary.md`.
